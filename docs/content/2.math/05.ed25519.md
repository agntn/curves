## The cofactor is back

ristretto255 hides the cofactor of edwards25519. Monero doesn't bother. Its keys are plain ed25519 points, 32 bytes each, and the 8 sits right there in the group. So `@agntn/curves/ed25519` keeps it too.

```ts
import { multiplyGenerator } from "@agntn/curves/ed25519";

multiplyGenerator(1n); // "5866666666666666…6666"
multiplyGenerator(0n); // "0100000000000000…0000"
```

All those sixes? That's y = 4/5, the base point of RFC 8032. The identity is `01` and zeros. And 32 zero bytes? In ristretto255 that's the identity. Here it's a point of order 4. Same bytes, other curve, other answer.

## Valid isn't the same as safe

Every canonical encoding decodes, whatever its order. A point with a piece of order 2, 4 or 8 in it is a fine point. It's also a lousy key. `isTorsionFree` catches it: l times the point has to land on the identity.

```ts
import { isTorsionFree, isValidPoint, multiplyPoint } from "@agntn/curves/ed25519";

const sneaky = "c7176a703d4dd84fba3c0b760d10670f2a2053fa2c39ccc64ec7fd7792ac037a";
isValidPoint(sneaky); // true
isTorsionFree(sneaky); // false
multiplyPoint(sneaky, 8n); // "0100000000000000…0000"
```

Monero's `check_address` wants two things. Not the identity, and nothing of small order. The identity is in the subgroup, so `isTorsionFree` waves it through. `isIdentity` does the other half.

## A Monero subaddress

Two points, one sum, one product. D = B + mG and C = aD. B is the public spend key, a the private view key. And m? Keccak of `SubAddr\0`, a and the two indices, reduced mod l.

```ts
import { addPoints, multiplyGenerator, multiplyPoint, reduceScalar } from "@agntn/curves/ed25519";

const spend = "1b3bd040020d3712ab84992b773d0a965134eb2df0392fb84af95de8a17be2ab";
const a = reduceScalar("49774391fa5e8d249fc2c5b45dadef13534bf2483dede880dac88f061e809100");
const m = reduceScalar(subaddressHash); // the 64 hex digits of that keccak

const d = addPoints(spend, multiplyGenerator(m)); // "8e4841533f2f07f9…9abd"
multiplyPoint(d, a); // "b833d78e77da6d8d…5269"
```

That's account 1, index 1 of a test wallet, and monero-wallet-cli shows its address there too. Keccak comes from [`@agntn/hashes`](https://hashes.agntn.dev). The address around the keys lives in [@agntn/keys](https://github.com/agntn/keys).

## Scalars

`reduceScalar` reads hex little-endian and reduces it mod l. 32 bytes is Monero's `sc_reduce32`, 64 bytes is `sc_reduce`, the one for a SHA-512. Monero runs every key through the first one, so it's not optional.

Everything else takes bigints from 0 to l - 1, like ristretto255. An RFC 8032 secret scalar sits above l after clamping. Reduce it first. On the base point the answer doesn't change.

Decoding follows RFC 8032 to the letter. y at or above p, a y with no x on the curve, a sign bit on x = 0. All three throw `Invalid ed25519 point`.

## Written from the specs, again

The encoding is RFC 8032. The additions and doublings are the ones ristretto255 runs on, the same file underneath. The tests hold it to the keys of RFC 8032 and to that Monero wallet. A local run against `@noble/curves` agreed on 300 random cases, small order points mixed in.

About 0.9 ms per multiply. Not constant time either. Puzzles yes, a wallet with money in it no.
