## Points in, points out

```ts
import { addPoints, liftX, multiplyGenerator, multiplyPoint } from "@agntn/curves/secp256k1";

const G = multiplyGenerator("1"); // "0279be667ef9dcbb…1798"
multiplyGenerator(3n); // "02f9308a019258c3…36f9"
addPoints(G, multiplyGenerator(2n)); // "02f9308a019258c3…36f9", 3G again
```

Points are SEC1 hex without `0x`, 33 bytes compressed or 65 uncompressed. Output is compressed unless you pass `{ compressed: false }`. A scalar is hex up to 64 digits or a `bigint`, from 1 to n - 1.

| Function | Does |
| --- | --- |
| `addPoints(a, b)` | a + b, as in a split key vanity address |
| `subtractPoints(a, b)` | a - b, the offset between two known keys |
| `negatePoint(p)` | same x, the other y |
| `multiplyPoint(p, k)` | k times p |
| `multiplyGenerator(k)` | k times G, the public key of k |
| `liftX(x)` | both points above x, even first |
| `isOnCurve(p)` | true or false |
| `convertPoint(p)` | between 33 and 65 bytes |
| `verify(sig, { digest, publicKey })` | true or false for an ECDSA signature |
| `recoverPublicKey(sig, { digest, recovery })` | the public key for a recovery ID |

## Half of G

What's G times the inverse of 2?

```ts
import { invertScalar, multiplyPoint } from "@agntn/curves/secp256k1";

invertScalar(2n); // "7fffffffffffffffffffffffffffffff5d576e7357a4501ddfe92f46681b20a1"
multiplyPoint(G, invertScalar(2n)); // "0200000000000000000000003b78ce563f89a0ed9414f5aa28ad0d96d6795f9c63"
```

Eleven zero bytes at the start of x. Out of 2^256 possible values. Make of that what you will.

## Scalars mod n

`addScalars`, `subtractScalars`, `multiplyScalars` and `invertScalar` work mod the group order and give 64 hex digits back:

```ts
addScalars("fffffffffffffffffffffffffffffffebaaedce6af48a03bbfd25e8cd0364140", "2"); // "000…001"
```

That first number is n - 1, so adding 2 wraps to 1.

## Verify an ECDSA signature from Bitcoin block 170

On 12 January 2009, Satoshi paid Hal Finney 10 BTC. The transaction in block 170 sent 40 BTC back to Satoshi. Input 0 spent the 50 BTC block 9 paid to Satoshi's key.

The transaction is `f4184fc596403b9d638783cf57adfe4c75c605f6356fbc91338530e9831e9e16`. Its input 0 signs the legacy `SIGHASH_ALL` digest below. That's a signature worth checking.

```ts
import { verify, recoverPublicKey } from "@agntn/curves/secp256k1";

const SATOSHI = "0411db93e1dcdb8a016b49840f8c53bc1eb68a382e97b1482ecad7b148a6909a5cb2e0eaddfb84ccf9744464f82e160bfa9b8b64f9d4c03f999b8643f656b412a3";
const digest = "7a05c6145f10101e9d6325494245adf1297d80f8f38d4d576d57cdba220bcb19";
const signature = "4e45e16932b8af514961a1d3a1a25fdf3f4f7732e9d624c6c61548ab5fb8cd41181522ec8eca07de4860a4acdd12909d831cc56cbbac4622082221a8768d1d09";

verify(signature, { digest, publicKey: SATOSHI }); // true
verify(signature, { digest, publicKey: SATOSHI, lowS: true }); // true
recoverPublicKey(signature, { digest, recovery: 1 }); // "0311db93e1dcdb8a…a6909a5c"
recoverPublicKey(signature, { digest, recovery: 0 }); // "02fa0afca078065d…c316d323"
```

Why do both recovery IDs return a key? Each returned key verifies the signature. Recovery 1 gives Satoshi's key in compressed form. Recovery 0 gives another verifying key. One signature, two keys. Only one of them paid Hal. Compare the recovered key with the one you expect, using the same encoding.

The signature is `r` followed by `s`, as 128 hex digits without `0x`. Unpack a DER signature first. Hash the message yourself and pass the digest as hex without `0x`. The digest can be 1 to 64 bytes. Beyond 32 bytes, only the leftmost 256 bits count.

`lowS: true` rejects `s` above n / 2, as in Bitcoin's BIP 62 and BIP 146. This signature has a low `s`, so it passes either way. The default is `false`, unlike noble and libsecp256k1, because SEC 1 accepts either `s`.

Recovery IDs run from 0 to 3. Bit 0 selects the parity of the y coordinate of R. Bit 1 selects x = r + n, which requires r below p - n. IDs 2 and 3 almost never work on a real signature. For this signature, both throw because no such point exists.

Recovered keys are compressed SEC1 hex by default. Pass `compressed: false` for an uncompressed key. Verification and recovery take public input. Signing isn't in this library yet.

The [playground](/playground) has the same signature behind the `block 170` chip.

## What it refuses

```text
subtractPoints(G, G)                                    // The result is the point at infinity, which is no public key, as with P minus P
multiplyPoint(G, "0")                                   // Scalar must be hex without 0x or a bigint, from 1 to the curve order minus 1
negatePoint("02000…0005")                               // Invalid SEC1 secp256k1 public key
verify("00", { digest, publicKey: SATOSHI })            // Signature must be 128 hex digits without 0x, r then s
verify(signature, { digest: "", publicKey: SATOSHI })   // Digest must be hex without 0x, 1 to 64 bytes
```

No point of secp256k1 has x = 5, so the compressed form above is no point at all. `isOnCurve` says `false` for it instead of throwing. A coordinate at or above p is refused too, as SEC 1 asks.

For `r` or `s` outside 1 to n - 1, `verify` returns `false`. Recovery throws `r and s must both be from 1 to the curve order minus 1`.

For the block 170 signature, recovery 2 throws `No point of secp256k1 has x = r + n, so recovery 2 fails`. Recovery 3 reports the same problem with its own ID.

## Written from the specs

The domain parameters come from SEC 2, section 2.4.1. The encodings follow SEC 1, sections 2.3.3 and 2.3.4. Points multiply in Jacobian coordinates, one inversion per result. No `@noble/curves` underneath, though the tests hold every result to it.

Verification follows SEC 1 section 4.1.4, and recovery follows section 4.1.6. All 574 secp256k1 Wycheproof P1363 vectors for SHA-256 and SHA-512 get the expected answer. Recovery tests also match results frozen from `@noble/curves` 2.4.0.

Is it as fast? For G, faster. The first multiply of G builds a table of 960 multiples, about 9 ms. Every one after it is at most 64 additions and no doubling, about 0.2 ms. noble takes 0.4 ms, but its `multiply` runs in constant time and this one doesn't, so this is a race noble wasn't running. Any other point still doubles and adds, about 1 ms. Nothing here runs in constant time, so keep real keys away from it.

## Over MCP

`curves_secp256k1_compute` does `add`, `subtract`, `negate`, `multiply`, `lift`, `check`, `verify` and `recover`. Scalar math stays in the library.

```text
{"operation":"lift","even":"0279be667ef9dcbbac55a06295ce870b07029bfcdb2dce28d959f2815b16f81798","odd":"0379be667ef9dcbbac55a06295ce870b07029bfcdb2dce28d959f2815b16f81798"}
```

For `verify`, pass the public key as `point`, plus `digest` and `signature`. You can also pass `lowS`. For `recover`, pass `digest`, `signature` and `recovery`. You can also pass `compressed`.

The CLI uses the same inputs. Running `curves secp256k1 verify` with Satoshi's key, digest and signature above returns:

```text
{"operation":"verify","valid":true}
```
