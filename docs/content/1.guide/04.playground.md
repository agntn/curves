## Try it without installing anything

The [playground](/playground) imports `@agntn/curves` into the page and runs the tool executors right there. Pick an operation, fill the fields, read the answer. Nothing leaves the tab.

Every state is a link. Change a field and the address changes with it, so a curve and its question can go into a chat or an issue as is. Opening the link runs the same call again.

What does it show? The call twice, once as a `curves` command and once as the JSON a model sends. Then the answer, with the full tool response one click away.

## Polkadot keys too

The sr25519 tool is there with the other two. One chip loads the Substrate dev seed with `//Alice` hanging off it, and verify says yes to her signature over `hello`. Now hit `one bit off`. One flipped bit and it's a plain `false`.

Sign twice and you get two different signatures. Bug? No, that's schnorrkel mixing fresh randomness into the nonce. Both verify.

Keypair and derive start from exactly one key, so the `from` row picks which. Derive can start from a seed too, and its hard child shows a seed of its own. Ask for a hard child from a public key and the tool says no. Fair enough, hard needs the seed or the secret.

## ECDSA signatures

`secp256k1 / sign` opens with secret 1 over the block 170 sighash. Not Satoshi's signature. Just one anybody can make, because everybody knows secret 1.

Reload and sign again. Same bytes, RFC 6979 sees to that. Paste the signature into `secp256k1 / recover` with the recovery ID it shows, and G comes back.

The `secret 1` and `secret n - 1` chips show up on sign only. n - 1 is the largest secret there is, and its public key is minus G.

## BIP340 signatures

Three leads: `bip340 / keypair`, `bip340 / sign` and `bip340 / verify`. The `pi message` chip loads the BIP vector that signs pi's hex digits with a key made of e. `empty message` signs no bytes at all. Both fill every field, secret and aux_rand included, so sign gives the BIP's own bytes.

Now hit `fresh random`. The random field goes empty, and each run mixes 32 new bytes into the nonce. Different signature every time. Do they all verify? They do.

`one bit off` waits on verify, where there's a signature to break.

## Ed25519 signatures

Three leads this time: `ed25519 / keypair`, `ed25519 / sign` and `ed25519 / verify`. The `RFC 8032 test 1` and `RFC 8032 test 2` chips fill all of them, secret included. Test 2 signs a single byte, `72`.

Sign either one and hold it next to the RFC. Same bytes. Reload and sign again. Still the same bytes. Boring, and that's the point.

The `order 8 key` chip is a lousy key with a surprising signature. It verifies under ZIP 215. Tick the strict checkbox and it fails. That chip and `one bit off` show up on verify only, where there's a signature to break.

The secret sits in the address bar like every other field. Fine for RFC vectors. Not for a key you care about.
